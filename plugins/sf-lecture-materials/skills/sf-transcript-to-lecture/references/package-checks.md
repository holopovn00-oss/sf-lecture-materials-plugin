# Машинная проверка текстового комплекта

Команда доступна в самостоятельном `scripts/handoff.py`; Python 3.11+, стандартная библиотека. Она только читает файлы. `build` и `check` сохраняют прежние интерфейсы.

```powershell
python scripts/handoff.py check-package --review 'C:/Task/text-v2/text-review.json' --previous-review 'C:/Task/text-v1/text-review.json'
```

Для первой версии опусти `--previous-review`. При его отсутствии история помечается `NOT_REQUESTED`, а не проверенной. Все файловые ссылки имеют вид `{"path":"C:/Task/file.json","sha256":"64 шестнадцатеричных символа"}`. Используй абсолютный существующий путь и SHA-256 фактических байтов; пример хеша не является допустимым значением.

## Обязательные данные

`text-review.json`:

- `schema_version`: `"1.0"`.
- `artifacts`: ровно пять файловых ссылок — `sources` (source-blocks.json), `lecture` (lecture-text.json), `markdown` (lecture-text.md), `source_manifest` (source-manifest.json), `review` (text-review.md).
- `semantic_review`: `status` со значением `COMPLETED`, `INCOMPLETE` или `NOT_PERFORMED`; `covered_source_ids` — уникальные известные ID; `open_issues` — массив открытых замечаний. Для `COMPLETED` требуется записанное покрытие всех исходных ID, включая удалённый шум. Наличие этого списка не доказывает, что проверка выполнена.
- `decisions`: массив записей решений; при отсутствии решений — `[]`.

`source-manifest.json` содержит непустой массив `files`. У каждой записи: `path`, `sha256`, `order` (1, 2, … в порядке массива), непустое `extraction` с фактическим способом чтения. Повтор файла запрещён. `source_uri` каждого исходного блока должен быть абсолютным путём одного из этих файлов. Проверяются байты исходников, а не только хеш извлечённых блоков.

## Решения

Каждая запись содержит:

- уникальный непустой `id`;
- `decision`: `proposed`, `correct` или `keep`;
- `execution`: `pending`, `applied` или `verified`;
- `basis`: непустое основание с точной формулировкой решения и доступным адресом/датой; скрипт проверяет наличие текста, не подлинность разрешения;
- `source_block_ids`: массив известных исходных ID;
- непустой массив `targets`.

Цель: `layer` (`text` или `title`), `expected` (точный защищённый фрагмент), `count` (ожидаемое положительное число его вхождений). Для `text` также нужен `id` итогового блока. Для `title` проверяется полное поле названия лекции. Это адресная защита фрагмента; она не устанавливает смысл остального текста и не защищает подписи будущего PDF.

`proposed` допускает только `pending`. Выполненное `correct` имеет `applied`, выполненное `keep` — `verified`. Для ожидающих решений наличие предложенного текста в лекции не требуется; для выполненных сверяется точное количество вхождений. Открытые решения остаются в `pending_decisions` результата, даже при техническом успехе комплекта.

При `--previous-review` прежние ID не могут исчезнуть. Изменение `decision`, `targets` или `source_block_ids` требует нового `basis` и поля `supersedes`, равного `handoff.digest(старая_запись)` — каноническому SHA-256 всей старой записи. Прежний файл не изменяется. Старые артефакты повторно не валидируются; проверяется переданная история решений и её файловый хеш. Наличие нового основания не является программным подтверждением согласия пользователя.

## Что означает результат

`PACKAGE_VALIDATED` подтверждает структуру LectureText, хеши и связи реальных файлов, точное равенство Markdown функции `to_markdown`, записанное покрытие и защищённые фрагменты решений. Чтение Markdown нормализует окончания строк CRLF/LF; слова, знаки и прочие пробелы не отбрасываются. Ошибка возвращает `BLOCKED` и код завершения 1.

Смысл остаётся `NOT_EVALUATED_BY_SCRIPT`; основание решений — `RECORDED_NOT_AUTHENTICATED`. Результат включает числа слов исходного текста, удалённого шума и лекции: непустые последовательности между пробелами, без допустимого процента сокращения. Числа не являются оценкой смысловой полноты. Прочитай `open_issues`, `pending_decisions` и содержательный отчёт перед передачей.
